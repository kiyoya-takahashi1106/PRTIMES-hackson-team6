# PR TIMES メディア自動推薦機能を実装してください

現在のコードベースを土台に、既存の「メディアリスト自動選択」機能を、過去の成功プレスリリースを活用した推薦ロジックへ変更してください。

新しい画面を一から作るのではなく、**既存UI・既存DB・既存APIをできる限り活用し、必要な箇所だけ変更してください。**

まずコードベース全体を調査し、関連するDB、API、メディアリスト選択処理、投稿処理、フロント画面の実装箇所を特定してから実装してください。

---

# 1. 実現したいこと

ユーザーがプレスリリースを作成した際に、過去の「似た企業 × 成功した投稿 × 内容が似ている投稿」を探し、それらが実際に掲載されたメディアを推薦したいです。

現在のフロントには、

- 手動選択
- 自動選択

が存在します。

**手動選択は変更しません。**

「自動選択」の内部ロジックを、今回の新しい推薦アルゴリズムへ変更してください。

ユーザー操作としては、

> 自動選択  
> → 推薦処理を実行  
> → おすすめメディアが選択される  
> → 「選択されたメディアを見る」で確認

という現在の体験を基本的に維持してください。

---

# 2. 推薦アルゴリズム

今回のプレスリリースに対して、以下の順番で推薦します。

```text
今回の企業・投稿
↓
直近5年 × 同業種 × 同企業属性
↓
各過去投稿の広告換算値を現在のデータから計算
↓
広告換算値 上位10% = 成功投稿
↓
今回の投稿と成功投稿のEmbedding類似度を計算
↓
類似度上位30投稿を取得
↓
その30投稿が実際に掲載されたメディアを取得
↓
類似度をもとにメディアをランキング
↓
自動選択結果として返す
```

---

# 3. 比較対象となる企業条件

過去投稿を検索する際は、以下を条件にしてください。

- 直近5年間
- 同じ業種
- 同じ企業属性

企業属性として想定しているカテゴリは以下です。

- 上場企業
- 地方企業
- 外資系企業
- ベンチャー企業
- 官公庁・団体

まず既存DB・既存コードを確認し、これらの情報がどのカラム・テーブルから取得できるか調査してください。

既存データから判定可能なものは、既存データを利用してください。

必要な情報が存在しない場合は、勝手な判定ロジックを作らず、既存構造との整合性を確認したうえで最小限の追加実装をしてください。

# 4. 成功投稿の定義

`success_flag` はDBへ固定保存しません。

広告換算値は時間によって変化するため、**自動推薦を実行するたびに、その時点のデータから成功投稿を判定してください。**

処理は以下です。

1. `直近5年 × 同業種 × 同企業属性` の過去投稿を取得
2. 各投稿に紐づく掲載メディア情報から、現在の広告換算値を計算
3. 広告換算値を降順に並べる
4. 上位10%の投稿を、その検索時点での「成功投稿」とする

広告換算値の計算方法は、まず既存コード・既存DBを調査してください。

すでに広告換算値を計算する処理が存在する場合は、必ずそれを再利用してください。

新しい独自計算式を勝手に作らないでください。

# 5. Embedding

過去投稿のEmbeddingは毎回計算せず、DBへ事前保存します。

Embedding対象テキストは以下を連結したものにしてください。

```text
title
+
lead_paragraph
+
body
```

`subtitle` は今回は使用しません。

Embeddingモデルは以下を使用してください。

```text
text-embedding-3-large
dimensions = 1024
```

OpenAI Embeddings APIを利用してください。

APIキーはコードへ直接書かず、既存の環境変数管理方式に合わせてください。

例：

```text
OPENAI_API_KEY
```

既存プロジェクトですでにOpenAIクライアントや共通API wrapperが存在する場合は、新しく重複実装せず必ず再利用してください。

# 6. PostgreSQL / pgvector

現在PostgreSQLを使用しています。

`release` テーブルに、各投稿のEmbeddingを保存する新しいカラムを追加してください。

想定：

```sql
embedding vector(1024)
```

必要であれば `pgvector` extensionを利用してください。

既存Migration方式を確認し、そのプロジェクトの作法に合わせてMigrationを作成してください。

DBを直接破壊的に変更しないでください。

既存データを失うMigrationは禁止です。

# 7. 過去投稿のEmbedding生成

既存投稿について、一度Embeddingを生成してDBへ保存する必要があります。

以下を実現してください。

- `embedding IS NULL` の投稿だけを対象にする
- `title + lead_paragraph + body` をEmbedding化する
- 1024次元Embeddingを`release.embedding`へ保存する
- すでにEmbeddingが存在する投稿は再計算しない
- 大量データを一度にAPIへ送らず、適切なバッチ単位で処理する
- API失敗時に全処理が壊れないようにする
- 再実行可能な処理にする

実行方法は、このプロジェクトに最も自然な形式を選んでください。

例：

- CLI script
- batch command
- management command
- migration後に実行する専用script

既存アーキテクチャに合わせて判断してください。

# 8. 配信時の推薦処理

自動選択を実行した際、以下の処理を行ってください。

### STEP 1：今回の企業情報を取得

- industry
- company category
- 現在日時

を取得する。

### STEP 2：比較対象を取得

以下を満たす過去投稿を取得する。

```text
直近5年
AND 同業種
AND 同企業属性
```

### STEP 3：広告換算値を計算

候補投稿について、現在の掲載メディア情報から広告換算値を計算する。

### STEP 4：成功投稿を抽出

広告換算値上位10%だけを残す。

### STEP 5：今回の投稿をEmbedding

今回投稿の

```text
title + lead_paragraph + body
```

をEmbeddingする。

今回の投稿のEmbeddingも、投稿保存後には`release.embedding`へ保存できるようにしてください。

### STEP 6：Cosine Similarityを計算

成功投稿のEmbeddingと今回投稿のEmbeddingの類似度を計算する。

類似度は、

```text
Cosine Similarity
```

を使用してください。

### STEP 7：TOP30を取得

類似度が高い成功投稿を上位30件取得する。

### STEP 8：掲載メディアを取得

TOP30の投稿について、`webclipping_list`など既存の掲載情報から、

> その投稿が実際に掲載されたメディア

を取得する。

### STEP 9：メディアをランキング

今回は複雑なスコアリングを行わず、**投稿との類似度を推薦の基準**にしてください。

同じメディアが複数投稿から取得された場合は重複表示しないでください。

同じメディアに複数の類似投稿が紐づく場合は、まずは

```text
そのメディアに紐づく投稿の中で最大のCosine Similarity
```

をそのメディアの推薦スコアとして扱ってください。

# 10. 推薦理由

可能であれば、推薦されたメディアについて最低限の推薦理由をフロントへ返してください。

例：

```text
○○メディア
今回と類似する成功プレスリリースで掲載実績があります
```

または、

```text
今回との類似度が高い成功投稿で掲載実績あり
```

PoC段階なので、複雑な説明生成機能は不要です。

推薦メディア名と簡単な推薦理由が確認できれば十分です。

# 12. エラー・例外処理

最低限、以下を考慮してください。

- OpenAI APIが失敗した
- Embeddingが未生成の過去投稿がある
- 比較対象となる過去投稿が0件
- 成功投稿が0件
- TOP30未満しか候補がない
- 掲載メディアが存在しない
- 同じメディアが複数投稿に登場する

推薦できない場合でも画面全体をエラーにせず、既存の自動選択ロジックへfallbackできる構造にできるなら、その方式を優先してください。

# 14. 実装方針

以下を優先してください。

- 既存コードを最大限再利用する
- UIを大きく変更しない
- 新しい推薦ロジックを既存の「自動選択」へ接続する
- DB変更はMigrationで管理する
- APIキーをハードコードしない
- Embeddingを毎回再生成しない
- 成功判定は毎回最新データから計算する
- 大量データを考慮した実装にする
- まずPoCとしてシンプルに動くことを優先する
- 不必要に複雑な抽象化をしない
