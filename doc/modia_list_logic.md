# PR TIMES メディア自動推薦機能を実装してください

現在のコードベースを調査した上で、既存の「メディアリスト自動選択」機能を、**過去の成功プレスリリースを活用したメディア推薦ロジック**へ変更してください。

新しい画面を一から作るのではなく、**既存UI・既存DB・既存APIをできる限りそのまま利用し、必要な箇所だけ変更してください。**

まず関連コード・DB構造を確認してから実装してください。

---

# 1. 実現したいこと

ユーザーが作成しているプレスリリースに対して、

**「同じような企業が過去に投稿した成功プレスリリース」の中から、今回と内容が似ている投稿を探し、それらが実際に掲載されたメディアを推薦する。**

現在のフロントには、

- 手動選択
- 自動選択

があります。

**手動選択は変更しません。**

既存の「自動選択」の内部ロジックを、今回の推薦アルゴリズムへ差し替えてください。

---

# 2. 推薦アルゴリズム

```text
今回の企業・投稿
↓
直近5年 × 同業種 × 同ipo_type の過去投稿を取得
↓
各過去投稿について広告換算値を最新状態から計算
↓
広告換算値 上位10% = 成功投稿
↓
今回の投稿をEmbedding
↓
成功投稿とのCosine Similarityを計算
↓
類似度上位30投稿を取得
↓
その30投稿が実際に掲載されたメディアを取得
↓
類似度をもとにメディアをランキング
↓
既存の自動選択結果として返す
```

---

# 3. 過去投稿の絞り込み条件

比較対象となる過去投稿は、以下をすべて満たすものとしてください。

```text
直近5年間
AND 同じindustry
AND 同じipo_type
```

企業属性について新しい独自カテゴリは作らず、**既存DBに存在する `ipo_type` を利用してください。**

まず以下の関係を既存DBから確認してください。

```text
release
↓ company_id
company
↓ industry_id / ipo_type_id
industry / ipo_type
```

既存のrelation・modelを可能な限りそのまま利用してください。

---

# 4. 広告換算値と成功投稿

`success_flag` や `percentile` はDBへ固定保存しません。

広告換算値は変化するため、**推薦実行時に毎回最新状態から成功投稿を判定してください。**

## 4.1 各掲載メディアと広告換算値を紐付ける

まず、

```text
各release
↓
掲載された各media
↓
その掲載に対応する広告換算値
```

を取得できる状態にしてください。

`webclipping_list` 等から各投稿の掲載メディアを取得し、広告換算値との既存の紐付け方法があるか調査してください。

既存DBに紐付けが存在しない場合は、

```text
release
×
掲載media
×
広告換算値
```

が取得できる最小限の構造を追加してください。

メディアを識別するときは、`site_name` 文字列だけで判定せず、**既存の `media_id` やメディアマスタが存在する場合は必ずそれを使用してください。**

## 4.2 投稿単位の広告換算値

各投稿の広告換算値は、

```text
投稿の広告換算値
=
その投稿に紐づく各掲載メディアの広告換算値の合計
```

として、推薦時に毎回計算してください。

その後、

```text
直近5年 × 同industry × 同ipo_type
```

の投稿を広告換算値順に並べ、

**上位10%をその時点での「成功投稿」**

と定義してください。

`success_flag` は保存しません。

Embedding対象は、

```text

+

+

```

としてください。

モデルは、

```text

```

類似度計算は、

```text
Cosine Similarity
```

を使用してください。

OpenAI APIキーはコードへ直接書かず、既存の環境変数管理方式に合わせてください。

例：

```text

```

# 7. 過去投稿Embeddingの事前生成

過去投稿は検索のたびにEmbeddingせず、事前生成してDBへ保存してください。

対象は、

```text
embedding IS NULL
```

の投稿のみとします。

```text
title + lead_paragraph + body
↓
OpenAI Embeddings API
↓
1024次元Embedding
↓
release.embedding
```

以下を満たしてください。

- Embeddingが既に存在する投稿は再計算しない
- 適切な単位でバッチ処理する
- APIエラーが発生しても再実行可能にする
- 大量の既存投稿を処理できる構造にする

実行方法は、既存プロジェクトに合わせてCLI / batch script等を選択してください。

# 8. 自動推薦時の処理

| 順番 | 処理 |
|---|---|
| **1** | 今回の企業の `industry` と `ipo_type` を取得 |
| **2** | `直近5年 × 同industry × 同ipo_type` の過去投稿を取得 |
| **3** | 各投稿の掲載メディアと広告換算値を取得し、投稿単位の広告換算値を計算 |
| **4** | 広告換算値上位10%を成功投稿として抽出 |
| **5** | 今回の `title + lead_paragraph + body` を1024次元Embedding化 |
| **6** | 成功投稿とのCosine Similarityを計算 |
| **7** | 類似度上位30投稿を取得 |
| **8** | TOP30が実際に掲載されたメディアを取得 |
| **9** | 類似度をもとにメディアをランキング |
| **10** | 既存の自動選択結果として返す |

---

# 9. 今回投稿のEmbedding取得方法

「メディア選択」の時点で、今回の`release`がDBへ保存されているか既存フローを確認してください。

### 保存済みの場合

```text
release.title
release.lead_paragraph
release.body
```

を取得してEmbeddingしてください。

### まだ保存されていない場合

フロント側で入力されている、

```text
title
lead_paragraph
body
```

を既存の自動選択APIへ渡し、その内容からEmbeddingしてください。

既存投稿として保存された後は、生成したEmbeddingを `release.embedding` に保存できる構造にしてください。

# 10. メディアランキング

類似成功投稿は**上位30件**取得します。

最終的に推薦するメディア件数は、**現在の自動選択機能で選択している件数に合わせてください。**

同じメディアが複数の類似投稿に登場した場合は重複表示しません。

そのメディアに紐づく投稿の中で、

```text
最大のCosine Similarity
```

を、そのメディアの推薦スコアとしてください。

今回は掲載回数などの追加スコアは使わず、**類似度のみを推薦順位に使用してください。**

---

# 11. データ不足時

以下の場合は、新しい推薦処理だけで無理に結果を作らないでください。

- 比較対象となる投稿が存在しない
- 成功投稿が存在しない
- Embeddingを持つ成功投稿が存在しない
- TOP30から掲載メディアを取得できない

その場合は、**現在存在する既存の自動選択ロジックへfallbackしてください。**

# 14. 実装方針

- 既存コード・DB・APIを最大限再利用する
- 新しい企業属性カテゴリは作らず、既存の`ipo_type`を利用する
- 手動選択は変更しない
- 自動選択のみ新ロジックへ変更する
- Embeddingは事前生成・保存する
- 広告換算値・成功判定は推薦実行時に毎回計算する
- メディアは可能な限り`media_id`で識別する
- PostgreSQL + pgvectorを利用する
- データ不足時は既存自動選択へfallbackする
- UIは大幅に変更しない
- PoCとしてまず正しく動くことを優先する
- 不必要な新規API・テーブル・抽象化を増やさない

- 推薦ロジックの実装箇所
- フロント変更内容
- 実行・テスト方法

を簡潔に報告してください。
